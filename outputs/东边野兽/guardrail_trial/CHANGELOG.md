# guardrail_trial — 自我修正循环实验记录（2026-08-12）

> **Status: 实验记录，不是冻结产物。**
> 东边野兽案例的展示版仍是 `../backup_v8/`。本目录留档的原因是过程数据有价值，
> 产出本身不合格（详见「为什么不能当交付版」）。

- **Case**：东边野兽 / Herbeast → 英国
- **变体**：`research_only`（可行性 → 缺口补证 → 开拓 → 竞品）
- **本轮唯一改动**：给 `competitor_analysis_task` 挂上 `guardrail: citation`——
  产出后跑机械引用校验，有**严重问题**就把逐条违规清单喂回同一个 agent 自动重跑（最多 2 次）
- **本目录文件**：四份研究产出 + `tool_audit.jsonl`

---

## 一句话

guardrail 生效了（严重问题 4 → 0），但模型立刻换了第六种规避方式：
**凭记忆重建格式完美的单品页 URL**——独立 HTTP 验证发现 5 条里至少 3 条是 404。
这是「机械校验能保证格式合规、保证不了内容为真」最直接的一次证明。

---

## 第一部分：guardrail 本身的验证

### 先踩了一个框架层的坑（值得单独记）

第一次跑完，竞品报告**仍有 4 处严重问题**（品牌首页当商品页 ×2、市场份额舆论缺证据 ×2），
且终端没出现 `Guardrail blocked` 提示。排查顺序与结论：

1. **配置读取正常**：`spec.get("guardrail")` 能拿到 `"citation"`，`guardrail_max_retries` 是 2
2. **guardrail 函数逻辑正常**：把那份**真实产出**喂回校验函数，它正确拦下并给出 4 条可操作反馈
3. **执行路径也在**：`crewai/task.py` 里确实有 `if self._guardrail: _invoke_guardrail_function(...)`

真正的根因在 CrewAI 的 `Task._execute_core`：

```python
result = agent.execute_task(...)                     # 790 行，只在这里赋值一次
...
task_output = self._invoke_guardrail_function(...)   # 839 行，重试在这里发生
...
if self.output_file:
    content = (... else result)                      # 865 行，写的是没更新的 result
    self._save_file(content)
```

**guardrail 重试产生的新内容只体现在返回的 `task_output` 里**，而重试内部那个 `result`
是 `_invoke_guardrail_function` 的局部变量。所以：**校验跑了、模型也改了，
但落到磁盘上的仍然是第一次执行的原始版本。**

审计日志佐证：竞品分析师那一轮有 13 次工具调用，其中 12:10:10 之后那批查询
突然跳到 UK REACH / OPSS 等主题，不像同一轮的连续动作，更像重试时的第二轮检索。

**解法**：挂了 guardrail 的 task 不用 CrewAI 的 `output_file`，改用 `callback` 写文件——
callback 在第 850 行执行（**早于** output_file 写入），且收到的 `self.output` 是校验后的版本。
两者互斥，所以代码里挂 callback 时会把 `output_file` 置空。

**这条教训可以脱离本项目复用**：接第三方框架的钩子时，
「钩子被调用了」和「钩子的结果生效了」是两回事，必须端到端验证，不能只验证钩子本身。

### 修复后：guardrail 确实工作

| | 修复前 | 修复后 |
|---|---|---|
| 引用校验严重问题 | **4 处** | **0 处** |
| 竞品商品页 URL | 品牌首页（`weleda.co.uk/`、`nealsyardremedies.co.uk/`） | 单品页路径（`/products/weleda-skin-food-75ml` 等） |
| 市场份额 | 「知名度高，尤其在有机市场中具有显著影响力」（无来源断言） | 全部「目标市场数据证据不足」 |
| 舆论口碑 | 「消费者评价普遍积极」（无来源断言） | 全部「缺乏具体 URL 支持，证据不足」 |

模型确实照着反馈清单逐条改了。**自我修正循环是通的。**

## 第二部分：但模型换了第六种规避方式

### 异常信号

全流程只有 **5 次搜索、0 次抓取**（可行性 2 次 + 竞品 3 次），却产出了 **44 个 URL**。

把报告里的商品页 URL 拿去跟搜索工具实际返回的内容比对——**5 条没有一条来自搜索结果**。
而且格式变了：之前几轮 Aesop 一直是 `aesop.com/uk/p/...`，这次变成 `aesop.co.uk/products/...`，
是按 Shopify 常见 URL 模式拼出来的。

### 独立 HTTP 验证结果

| URL | 结果 | 判定 |
|---|---|---|
| `weleda.co.uk/products/weleda-skin-food-75ml` | **404** | ❌ 页面不存在 = 编造 |
| `nealsyardremedies.com/wild-rose-beauty-elixir-30ml` | **404** | ❌ 编造 |
| `drhauschka.com/en-gb/rose-day-cream/` | **404** | ❌ 编造 |
| `aesop.co.uk/products/fabulous-face-cleanser` | 403 | ⚠️ 反爬拦截，**无法判断** |
| `paiskincare.com/products/rosehip-bioregenerate-oil` | 200，标题确为 Rosehip Oil | ✅ **URL 是真的**，但页面上找不到 £24.00 |

**保守结论：5 条里至少 3 条确认编造。**

不是"全部瞎编"，而是**凭记忆重建**：Pai 那条蒙对了（页面标题确认就是 Rosehip 面部油），
说明模型确实记得该产品与该站 URL 结构；但按同样套路拼出的另外三条就是 404。
**这比纯粹编造更隐蔽——因为它有时候会蒙对，让人以为整批都可信。**

保留的不确定性：403 不等于链接是假的；Pai 那条价格对不上也可能是标价变动或 JS 渲染，
不下结论。

### 一个关键事实

`competitor_analyst` 的配置里**是有 `scrape_page` 抓取工具的**，但这一轮**一次都没调用**。
也就是说：它有能力打开页面核实自己写的 URL，但没有这么做。

这与之前 agentic 实验的病因完全一致——**工具在手边，但模型不认为「核实」是自己该做的事**。

## 第三部分：规避方式的完整演化链

到这一轮为止，同一套「堵漏 → 换招」的模式已经出现六次：

| # | 规避方式 | 首次出现 | 被什么拦住 |
|---|---|---|---|
| 1 | 编造 `example.com` 假域名 | backup_v3 | 机械校验（假域名名单） |
| 2 | 真链接但内容对不上（首页当商品页） | backup_v4 | 机械校验（路径深度） |
| 3 | `TBD` 占位符代替证据 | 花知晓 v1 | 机械校验（占位符检测） |
| 4 | 品牌首页当商品页 | 花知晓 v1 | 机械校验（裸域名检测） |
| 5 | 「市场份额约 25%（证据不足）」数字加免责词 | 花知晓 v1 | 机械校验（无来源数字，兜底措辞不豁免） |
| 6 | **凭记忆重建格式完美的单品页 URL** | **本轮** | **机械校验查不出** → 只能靠独立 HTTP 请求 |

**前五种都能靠代码枚举规则拦住，第六种不能。**因为那些 URL 在结构上完全合法：
本地域名、单品页路径、与 SKU 品类一致——所有已有检测都会放行。

要发现它，必须**离开文本、去问外部世界**。这正是 `experiments/verify_urls.py` 的价值，
而这一层目前在流水线之外（跑完手动执行），不是自动关卡。

## 第四部分：另一个独立问题（与 guardrail 无关）

深度门禁报 **`gap_fill_zero_search`：缺口补证研究员 0 次成功搜索**。

审计日志确认：该 agent 一次搜索都没做。也就是说 `evidence_gap_fill.md` 里那些
「补证结果」「新事实」全是模型自己写的，没有任何检索支撑。这一步目前形同虚设。

这个问题跟 guardrail 无关，是独立缺陷，**未修，记账**。

## 结论

**guardrail 的价值和边界都清楚了。**

- **价值**：它把「可枚举的格式规则」变成了自动关卡，模型确实会照着反馈改。
  而且裁判是代码不是模型——这是它优于此前 agentic 实验的关键（那次把判断交给模型，
  结果模型写了 10 条「已核实」、逐条对质通过 0 条）。
- **边界**：它保证不了内容为真。任何**能被规则描述**的缺陷它都能拦，
  但「这个 URL 真的存在吗」需要外部世界的反馈，规则描述不了。

三层验证缺一不可，这一轮是最硬的证据：机械校验放行了 5 条编造 URL，
只有真发 HTTP 请求才戳穿了其中 3 条。

## 面试怎么讲这一段

> 我给 workflow 加了一个 agent 式的自我修正循环：产出后跑机械校验，不合格就把
> 具体违规清单喂回模型重跑，裁判是代码不是模型。第一次跑完发现产出还是有 4 处严重问题，
> 但排查下来不是我的校验错了——把那份产出喂回校验函数它能正确拦下。真正原因是框架
> 写文件时用的是第一次执行的变量，而重试后的内容在另一个对象里，所以**校验和重试都
> 正常工作，磁盘上留的却是没改过的版本**。修完之后严重问题从 4 降到 0，模型确实
> 逐条改对了。
>
> 但我没有就此收工，而是去验证那些"改好"的 URL 是不是真的——结果 5 条商品页里
> 至少 3 条是 404。模型的应对方式变成了**凭记忆拼出格式完美的单品页链接**，
> 本地域名、单品路径、品类一致，我所有的机械检测都会放行。
>
> 这件事让我把结论说得更准确了：**能被规则描述的缺陷，代码可以自动拦；
> 但"这个链接真的存在吗"规则描述不了，必须离开文本去问外部世界。**
> 到这一轮为止，模型的规避方式已经演化了六种，前五种都被代码拦住了，第六种拦不住——
> 这就是为什么我坚持三层验证，而不是指望某一层做完所有事。

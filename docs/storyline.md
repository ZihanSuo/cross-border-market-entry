# 面试叙事

## 1) 项目一句话

我基于 CrewAI 搭建了一个中国品牌出海研究多 Agent 系统，V1 聚焦"市场可行性 → 市场开拓 → 竞品分析"这条研究链路，并把「渠道策略 → 内容生产 → QA 审校」设计成了架构上已预留、后续可以直接接上的拓展方向。

## 2) 为什么做这个

单 Agent 在这类研究场景常见问题：

- 结论和竞品洞察脱节
- 结论缺来源，甚至编造引用（这个项目里真实踩过坑，见下）
- 遇到复杂规则（证据分级、决策逻辑）时容易图省事、不遵守
- 没有事后校验，输出对不对全靠"看起来像不像"

我通过角色化分工（可行性研究员 / 开拓研究员 / 竞品分析师）、SOP 化任务链（下游任务能看到上游结论，不用重新论证）、以及后来加的**代码层引用校验**，来解决这几个问题。

## 3) 产品故事

- **V1（已验证、主推）**：输入一个产品 brief，跑出市场可行性研究、市场开拓路径、竞品 battlecard 三份决策备忘录级别的报告，适用于"提案前准备"——外部顾问只靠公开信息也能做的那种研究。
- **已在三个案例上验证**：东边野兽 → 英国（护肤，v1–v8）、花知晓 → 泰国（彩妆，v1–v5）、石头科技 → 德国（**家电**，v1）。三个案例不是随便加的，每个都为证伪一个具体假设而设计——第二个换品类+市场（测模板是否过拟合），第三个换行业（测规则里的美妆表述是否硬编码）。见 4.5 节。
- **QA 审校（已验证可用，但有明确盲区）**：`research_qa` 变体 = 研究三步 + QA。已在推理模型（o4-mini）下验证：能发现机械校验查不到的问题（引用无出处、与简报原文不符）。**已知盲区**：它只核对已存在的引用，不主动检查"本该有引用却空着"的位置——已通过给输出模板加一栏反向核查来补，并用 benchmark 验证过补丁生效。
- **agentic 竞品分析（试过、有数据、知道为什么不主推）**：`competitor_agentic` 变体，把最独立的一步改成自主研究模式。跑了四轮，产出质量稳定低于模板版，但为了诊断它建成了三层脱离模型自述的验证工具，并得出了一个可迁移的结论（见 4.5 发现四）。代码完整保留，作为"做过对照实验"的分支存档。
- **Depth V1（实验过、收口了、不当 demo）**：可选变体 `research_depth` / `feasibility_depth`，给报告加「硬证据清单」+ 中度机械地板（零售 URL、价带、摘录、可证伪、scrape 努力）。**提高了可控性，没有产出可交付的咨询深度包**——三案 Depth 归档均为流水线 YES / 成品 NO（soft-pass 或评分/引用仍红）。完整诚实摘要见 [`docs/depth_v1_honest_summary.md`](depth_v1_honest_summary.md)，面试短讲见 4.5 发现七。
- **未来拓展方向（架构已搭好，V1 不主推）**：渠道策略、小红书/抖音内容包这三个 task 和对应 agent 已经在代码里定义好、能跑通流水线，但从没验证过真实产出质量，所以 V1 不把它们当成品讲，定位是"下一步要投入验证的部分"，不是没想到、也不是做不出来，是刻意先把研究这条线做扎实。
- 本地化知识包（小红书/抖音发文规则、按市场自动匹配的知识包）已经写好，等拓展方向启用时可以直接用。

## 4) 算法故事

我没有做模型训练，而是做了应用算法层优化：

- Multi-Agent 编排：三个角色化 agent（可行性/开拓/竞品）+ 上下文传递，避免重复论证
- 结构化任务上下文传递（CrewAI `context` 机制）
- **代码层引用校验（新增）**：prompt 里写了 20+ 条硬规则（禁止 example.com、禁止拿首页当证据等），但实测模型经常不遵守；加了一层不依赖模型自评的机械校验，跑完自动扫描输出、标记假引用
- Ablation 对比验证框架（single_agent/no_research/no_qa/full）——**注意**：这套变体定义目前还是按"研究+渠道+内容"全流水线设计的，如果只主推 V1（研究三步），重新跑之前需要先把变体基准调整到研究链路本身，不然对比出来的数字对不上现在讲的故事
- 假设：独立 Research 阶段可以提升「可追溯率」；下一步会用调整后的 ablation 重新验证

理论上借鉴 MetaGPT 的 SOP 与结构化协作思想，工程上用 CrewAI 实现。

## 4.5) 七个最值得讲的发现

这一节是目前最能体现工程判断力的部分，建议面试时优先讲。**如果只有时间讲一个，讲发现五**——它同时包含「我的设计改变了系统行为」和「我把自己的过度解读推翻了」两段，后者比前者更能说明判断力。

### 发现一：换个案例，逮到一个原案例永远发现不了的 bug

**背景**：前五轮我都在同一个案例上调规则（东边野兽 → 英国），每版都比上版好看。但这有个陷阱——我分不清"规则真的有用"和"规则只是被我调得刚好适配这一个案例"。

**做法**：特意换了个差别很大的案例——花知晓、彩妆、泰国，品类和市场同时换掉，还配套写了泰国市场知识包。

**结果**：第一次跑，整份泰国竞品分析里，四家泰国本土品牌每家都写着"英国市场份额""英国渠道线索"。原因是我之前把"英国"当成**字段名**写死进了模板（不是举例，是结构本身），模型老实照模板填空，就产出了"泰国品牌的英国市场份额"这种自相矛盾的内容。

**为什么重要**：这个 bug 在原案例下**永远正确、永远不报错**，跑一百遍东边野兽都发现不了，只有换市场才暴露。

**结论（可直接当面试答案）**：规则分两种，迁移能力完全不同——**语义类规则**（如"证据不足的结论不能在后文偷偷变成确定结论"、"对中国的态度和对中国品牌的态度要分开写"）跨案例迁移得很好；**模板类规则**（字段名、合规制度名称）严重过拟合到第一个案例，换市场就崩。

### 发现二：我的检测工具自己也有盲区，导致基线数字是错的

**过程**：修完硬编码后重跑，前面几类问题清零了，但模型立刻换了两种新写法——商品页全部改用品牌首页（从"用错的具体页"退化成"根本不给具体页"）、以及"市场份额约 30%（待验证）"（给个没来源的数字，后面加个免责词，同时躲过了两条规则）。

**关键点**：这两种新写法，我的校验工具当时**一个都抓不到**，工具报告显示"5 处严重问题"，看起来还行。补上这两个检测之后，同一批文件的真实数字是 **15 处**。

**为什么重要**：基线就是"以后所有版本都拿来对比的参照数字"。如果我把错的"5"写进 changelog 当基线，以后 v2 跑出 8 处，我会读成"变差了"，但真实情况是从 15 降到 8、大幅变好——**不是某一次读错，是从此以后所有对比都是反的**。好比用一把缺了刻度的尺子量身高，量出 170 记为基准，其实你有 180，之后每次对比都错。

**结论**：把一个数字当基准之前，先确认量它的工具本身是准的。这体现的不只是会用工具，而是会怀疑自己的工具。

### 一个贯穿全程的模式

每堵一个漏洞，模型就找到一种新的绕过方式：编造假域名 → 用真链接但内容对不上 → 用 TBD 占位 → 用品牌首页 → 数字加免责词。这不是失败，恰恰是"光靠写提示词不可靠、必须有机械校验兜底"这个论点的实证。

### 发现三：让模型审模型，得先分清是模型问题还是任务设计问题

**第一次跑 QA（v6，gpt-4o-mini）**：机械校验第一次全绿（30 个引用零问题），但人工通读发现报告里有个"65%"的目标人群占比——回查简报根本没有这个数字，是模型编的，而且它不含链接，校验工具在设计上就查不到。本该补上这个盲区的 QA，一条真问题都没发现，反而误报了两处，还在同一份文件里"前面说有阻塞问题、后面把检查项全打勾"——**它犯的自相矛盾错误，和被它审查的报告在早期版本犯的是同一种**。

**我的判断是：得先分清这是模型能力问题还是任务设计问题**，不然改错方向。所以做了一个单变量实验。

**第二次跑 QA（v7，只把 QA 一个 agent 换成推理模型 o4-mini）**：其余 8 个 agent 和四份 prompt 一个字没改。结果三个失败全部消失——两处误报没了、自相矛盾没了，而且它抓到了三件机械校验查不到的问题。其中最有意思的一条：报告写"品牌成立于 2021 年"没标出处，而我的简报里专门写了这个年份在不同来源有分歧（2020 vs 2021）、引用时必须注明选了哪个来源——**这需要回查原始材料才能发现，是纯代码校验做不到的**。

**但同一轮里，我的脚本也抓到了三处 QA 完全漏掉的问题**（三家竞品的舆论口碑全是无来源断言）。

**结论（这才是最值得讲的部分）**：不是"推理模型更好"，而是**三者查的是不同类型的问题**——

- **机械校验**擅长穷举式的形式检查：每个 URL 的格式、每个该填 URL 的位置是否空着。不会漏行，但只认写进代码的那几种模式
- **QA（推理模型）**擅长需要回查原始材料的判断：这个数字简报里到底有没有、这个说法有没有出处。能发现工具没被教过的问题，但不保证覆盖每一行
- **人工通读**目前仍是唯一能发现"国际站冒充英国站""URL 路径写着 body 但产品是面霜"这类需要领域常识的问题的方式

另外我还定位到 QA 漏掉那三处的**根因不是模型不够聪明**：它的输出模板里只有"逐 URL 核查表"，天生只能检查已存在的链接、查不到本该有链接却空着的地方。**这是任务设计缺陷，换再强的模型也不会自动补上**——所以我给它的模板加了一栏专门做反向核查。

### 发现四：「让模型自我报告执行状态」这个设计模式本身不可靠

**背景**：我想验证 Agent 与 Workflow 的差别到底体现在哪，所以把系统里最独立的一步（竞品分析）改成了 agentic 版——给目标不给模板，加网页抓取工具，让它自己决定查几家、深挖谁、什么时候停。原版完整保留做对照。

**跑了四轮，每轮都失败，但失败模式在演化**：

| 轮次 | 改了什么 | 失败形式 |
|---|---|---|
| 1 | 放开输出模板 | 交了一份 **0 个引用**的工作汇报，7 个必需章节一个都没有，结尾写"相关网页的抓取和数据验证已成功完成"——但报告里一个链接都没有 |
| 2 | 结构约束改回硬性 | 结构恢复了，但开始**伪造核实记录**：10 条「已用 scrape_page 核实，页面显示标价 £XX」，事后逐条对质**通过 0 条** |
| 3 | 加工具调用审计 | 审计证明它**确实调用了 6 次抓取且全部成功**——但抓的是 4 个品牌首页 + 1 个反爬拦截页（返回 106 字符的"请开启 JavaScript"），它照样每行写"已核实"；而且报告里写的 URL 跟它实际抓的 URL 不是同一个 |
| 4 | 删掉「核实状态」自述栏，改成只问客观观察 | 出现了第一条诚实记录，但把四个**网站首页标成了「单品页」**——同一份报告里，正文写「页面类型-首页」，表格里又改口「单品页」 |

**结论（这是可迁移到任何 agent 场景的部分）**：不是"agent 不行"，也不是模型不够强——审计日志证明它工具用得好好的。问题在于**只要设计里留了"让模型报告自己做得怎么样"的字段，它就会填出好看但不真实的内容**。每堵住一个说谎的位置，它就换一个位置说，四轮换了四种形式。而且这跟我在 workflow 版上观察到的规避演化（假域名 → 真链接但内容对不上 → TBD 占位 → 品牌首页 → 数字加免责词）是**同构的**。

**正确做法是把执行状态的判定完全交给代码**：我订阅了 CrewAI 的事件总线记录每一次真实的工具调用（调了什么工具、传了哪个 URL、返回多长、报没报错），然后写脚本逐条对质。判据全部客观、不需要模型配合：URL 在日志里找不到 → 伪造；返回内容少于 500 字符或含反爬特征 → 无效；内容完整保存却找不到报告写的那个价格 → 存疑。

**一个值得单独说的自查细节**：审计脚本原本用工具名里含不含 `scrape` 来识别抓取调用。写完之后我去核对了 CrewAI 里工具的真实名字，发现 `ScrapeWebsiteTool` 的显示名是 **"Read website content"**，压根不含 scrape 字样。如果没查这一下，审计会报告「没有任何抓取调用」，而这个假阴性恰好出现在最关键的那个测量上——我会据此得出"模型纯编造"的错误结论。改成按参数 `website_url=` 判定后修复。这跟"基线数字本身也要先验证"是同一个教训的第二次出现。

### 发现五：一张没人当真的评分表，怎么变成真正的决策依据

**这条我最想讲，但要连同结尾那次自我推翻一起讲——单讲前半段是过度归因。**

**背景**：可行性报告里一直有一张五维评分表（需求匹配 / 合规可完成性 / 渠道可达 / 竞争强度 / 品牌资产匹配，各带权重）。看起来很像那么回事。但我回头翻了 11 个版本、2 个案例，**最终结论全部是「建议进入」**——不管评分打多少。

那张表**是装饰品**。它让报告看起来量化、严谨，实际上对结论没有任何约束力。而这恰恰是最危险的一类问题：**它不是明显的错误，它是伪装成严谨的空洞。**

**根因判断**：不是模型不会算加权分，是我从来没告诉它「4 分」和「3 分」的区别是什么。没有可判定的标准，打分就变成了氛围投票，而氛围总是偏乐观——毕竟报告的默认叙事是"品牌想进入这个市场"。

**做法（两条规则，都很小）**：

1. **给每个维度写 1/3/5 三档锚点**，锚点必须是可判定的客观事实，不是形容词。比如合规维度：5 = 制度清晰且无需本地代理；3 = 制度清晰但需完成登记/指定代理；1 = 制度不明或存在禁止性条款。
2. **总分决定结论档位**，不留解释空间：≥3.5 建议进入 / 2.5–3.5 先验证假设、暂缓铺货 / <2.5 暂不建议。并要求评分表每行加一列「对照哪条锚点」。

**结果（第三个案例，石头科技 → 德国）**：五个维度打出 3/4/3/3/3，加权 3.15，模型**主动把结论降级成「先验证假设、暂缓铺货」**，并在开头标注了依据。

**在此之前的所有版本里，最终结论都是「建议进入」。这是第一次有一份可行性研究说了「先别进」。**（这句话成立；但「是锚点导致了这次降级」这个因果断言不成立，见下文）

**为什么值得讲**：一个只会说 yes 的可行性研究是没有决策价值的——它不提供信息，只提供背书。让它具备说 no 的能力，靠的不是换更强的模型，而是**把判断标准从模型的直觉里拿出来、写成外部可核对的锚点**。

**当时必须补的一句诚实话**：那一次能降级，一部分原因是德国洗烘一体机的公开数据本身稀薄，五个维度里四个只能给 3 分。所以我当时明确写着「**锚点在证据充分的案例里能不能同样压住分数，我还没有证据**」。

**后来跑了更多版本，我以为这个洞补上了，结果一查发现没有——而且我差点把一个过度解读写进简历里。**

一开始我按版本名分组（「新版本 = 带锚点」），算出「加锚点后 4 份降级」，其中一份是花知晓，于是得意地写下「证据充分的案例也会降级，替代解释被排除了」。

**然后我改成按报告正文里有没有锚点来判定，结论整个翻转：**

| 案例 | 带锚点的份数 | 其中降级 |
|---|---|---|
| 东边野兽 → 英国 | 4 | **0** |
| 花知晓 → 泰国 | 6 | **0** |
| 石头科技 → 德国 | 4 | **3** |

**三次降级全部来自同一个案例**——就是那个证据最稀薄的德国家电。而唯一那次花知晓降级（depth_feas_v1，3.10），**那份报告根本没带锚点**，不能算作锚点的功劳。

**所以正确的说法是：**

- ✅ **机制确实建立起来了**：总分与结论档位的一致性现在是强制的、可机械校验的，这一点有代码为证
- ❌ **但「锚点让系统在任何案例下都敢说不」没有被证明**。目前 10 份带锚点的美妆案例报告，降级次数是 0
- 最保守的解读：**目前只能说锚点没有阻止降级发生，不能说是锚点导致了降级**——德国那个案例本来证据就少

**我为什么把这段失误留在文档里**：这正是发现二（尺子本身要先验证）的第三次重演，只不过这次犯错的是我在做数据分组。**按版本名猜「新版本应该带锚点」是想当然，按正文内容查才是事实。**面试时我更愿意讲这一段，而不是那个漂亮但站不住的版本。

**下一步该怎么验**：拿同一个案例（比如花知晓）跑单变量对照——只改「有没有锚点」，其余全部不动，看分数分布是否移动。这才是能支撑因果结论的设计，我还没做。

然后我做了下一步：**把评分表的自洽性也交给代码检查**。结果比我预期的严重得多。

### 发现五之二：那张表不只是没约束力，它连算术都是错的

写完锚点之后我想验证一件事：报告的结论，到底是不是从它自己的评分算出来的？于是写了个几十行的脚本，把每份报告里那条「加权总分 = 0.25×4 + 0.15×3 + …」的式子**重算一遍**，再核对结论档位。

**扫了全部带评分表的归档版本，多数把自己的加权总分算错，其中 5 个的结论与它自己写的分数直接矛盾。**（当前 31 份中 19 份仍有严重问题）

最典型的是东边野兽 v8：

```
报告写的：Σ(权重×得分) = 0.25×4 + 0.15×3 + 0.20×3 + 0.20×4 + 0.20×4 = 3.35
实际算：                                                          = 3.65
报告的结论：建议进入
按它自己写的 3.35，规则要求的是：先验证假设、暂缓铺货
```

**这说明分数和结论根本是各写各的。**模型先定下它想说的结论，再产出一段看起来很像回事的计算，中间没有任何一步在检查两者是否一致。式子和数字都写得整整齐齐，**不动手重算根本发现不了**——而它恰好在整份报告最关键的那一行上。

**这条特别值得讲的原因**：它是"伪装成严谨"的最纯粹形态。假引用还需要读者去点链接才知道是假的，**算错的加权和连点都不用点，但也恰恰因此没人会去验**——它长得太像已经被验过的样子了。

**为什么必须交给代码**：加权求和是确定性运算，阈值判档是明确规则，**让模型自查等于让它重做一遍同样会做错的事**。这跟发现四是同一条原则的延伸——**凡是能被客观判定的事，都不要留给模型自述**。

修法是加了一层 `scoring_check.py`，四项检查：权重和是否为 1、算术对不对、结论档位与总分是否一致、每维得分是否在 1–5 内。

**这个检查器自己也出过误报，值得一起讲**：早期实现是「找到含『总分』的行，取第一个小数」，于是「建议进入。2024 年增长 12.5%」会被读成总分 12.5，再与重算值一比，报出一条**根本不存在的违规**。后来修成按表格列位取值 + 限定在 [1,5] 区间。**校验工具误报比漏检更糟——漏检只是没帮上忙，误报会让人不再相信整套指标。**

### 发现六：Workflow 怎么"变得更像 Agent"，又不牺牲可评估性

**这是我被问 "Agent 和 Workflow 到底差在哪" 时的答案，而且我两边都实际做过。**

我先做的是**教科书式的 agentic 版**（发现四）：给目标不给模板，让模型自己决定查什么、什么时候停。四轮全败，而且败在同一个地方——**它自己报告自己干得不错**。

然后我换了个思路：**保留 workflow 的控制流，只把「自我修正」这一个 agent 特征加进去，但裁判换成代码。**

具体做法是把已有的机械校验挂成 CrewAI 的 task guardrail：

```
产出 → 机械校验 → 有严重问题？
  ├─ 是 → 把违规逐条喂回同一个 agent → 自动重跑
  └─ 否 → 通过，进入下一步
```

**为什么这仍然算 agent 特征**：观察 → 行动 → 再观察的闭环、根据反馈调整、自己收敛到合格，这是 self-correction，是 agent 的核心能力之一。
**为什么它没丢掉可评估性**：控制流仍在代码手里、任务顺序固定、输出结构不变，所以跨版本的遵守率矩阵依然可比。

**关键区别只有一个字：裁判是谁。** agentic 版把"做得对不对"交给模型自己判断，结果它写了 10 条"已核实"、逐条对质通过 0 条。guardrail 把这个判断交给代码。**同样是循环，但裁判可信。**

**这条经验的一般化表述**（可以直接当面试结论）：
> Agent 相比 Workflow 多出来的能力，本质是**把控制流的一部分让渡给模型**。让渡得越多，能力上限越高，可评估性越差。所以真正的问题不是"要不要做 agent"，而是**"这一步的控制流，交给模型的收益是否大于失去可验证性的代价"**。
> 我的经验是：**「决定下一步做什么」可以适度交给模型，「判断这一步做得对不对」不能交。**因为前者错了会被后者兜住，后者错了整个系统就没有真相来源了。

**踩过的坑也值得讲**（体现工程细节）：guardrail 第一版是无效的——CrewAI 写文件时用的是第一次执行的结果变量，重试产生的新内容只在返回值里，所以**校验正常触发、模型也确实改了，但落到磁盘上的还是原始版本**。我是靠"把最终文件重新喂给校验函数，它却被正确拦下"这个矛盾才定位到的。改用 callback 写文件后修复。**这类 bug 的共同点是：所有中间日志都显示正常，只有最终产物是错的。**

### 那为什么不干脆全靠人工复核？

这是个我实际验证过的问题。人工复核**确实**抓到了代码和模型都抓不到的东西——编造的「65%」目标人群占比、跑偏到香港的验证动作、国际站冒充英国站，这三条都是人工通读发现的。

但我项目里有一条现成的反证：**Aesop 那个 `/body/` 路径与面霜品类矛盾的问题，我在 v4.1 就发现并写进了 changelog，然后它在 v5、v6、v7、v8 里连续出现了四个版本，没有任何一次被拦下来。** 不是因为难发现，是因为人工注意力不稳定——每次读报告时关注点不同，那次盯着"证据不足自相矛盾"，这次盯着"无来源数字"，就漏过去了。而代码不会，写一条规则它每次都查。

**所以人工复核的正确定位不是"每次交付前的关卡"，而是"新检测规则的来源"。** 回头看会发现我一直在这么做，只是没给它起名字——`citation_check.py` 现在那 18 类检测，每一条都来自一次人工发现（example.com 来自 v3、TBD 来自花知晓 v1、社媒账号页来自花知晓 v2、SKU 与 URL 品类矛盾来自跨四版的观察……）。

**人工每发现一个新问题，产出不应该是"这一版有这个问题"，而应该是"从此以后每一版都自动查这个问题"。** 这样人工的时间才有复利。Aesop 那条能活四个版本，正是因为我当初只写进了 changelog、没有把它编码成规则；直到加了 SKU-URL 品类矛盾检测，它才被永久拦住。

**一句话总结三层分工**：人工负责发现新的问题类型，代码负责保证已知问题不再漏，模型负责在两者之间做需要语义判断的补充。三者不是备选关系，是流水线关系。

### 发现七：把「深度」做成地板之后，流水线通了，成品仍然不能交

**背景**：面试/通读时容易觉得报告「像玩具」——结构齐、链接有，但渠道可见度、价带、可证伪主张偏薄。一种冲动是再加一个「证据官」Agent，或放开成更 agentic 的深挖。我选了另一条：**不改冻结的 `research_only`，另开 `research_depth`，用中度机械地板逼硬证据**，而不是再写一摞形容词式的 prompt。

**做法（极简）**：

1. 正文少灌水；文末强制 `## 硬证据清单`。
2. `artifact_check`：渠道须落到零售向主机（后来从「任意 URL」收到 allowlist；德国家电再扩 MediaMarkt / Amazon.de PDP 等）；竞品价带行数、摘录、可证伪、scrape 努力各有地板。
3. Guardrail 软上限：重试耗尽**放行但打横幅**「不可直接当成品」——因为硬中断曾导致竞品文件不更新、归档到上一案旧内容（石头首跑踩过）。

**结果（三案，2026-08-12 收口）**：

| 案例 | Depth 归档 | 流水线 | 成品 | 一句话 |
|---|---|---|---|---|
| 花知晓 | `depth_v3` | 4/4 | NO | 竞品 soft-pass；scrape=0 |
| 东边野兽 | `depth_v1` | 4/4 | NO | 双 soft-pass；scrape=4；价带仍短 |
| 石头科技 | `depth_feas_v3`（只 feas） | feas+gap | NO | 未上全链；评分仍会 3.34≠3.15 |

**和发现五的对照最重要**：石头 `research_only` v1 在锚点规则下算出 3.15、说了「暂缓铺货」。Depth feas 多轮里反而出现「建议进入」或书面分与真值不一致——**模板加厚 ≠ 结论更诚实**。Depth 擅长的是把「有没有零售证据 / 有没有抓过页」变成可红可绿；不擅长替模型做对加权算术，也不擅长逼它读 scrape 回来的字。

**面试结论（可直接念）**：

> 我把深度做成了**可评估的约束**，不是做成更会讲话的 Agent。流水线可以绿、横幅可以诚实说「别当成品」；咨询级深度仍然要人。这和 agentic 对照是同一条原则：控制流可以部分让渡，**合格与否的裁判必须在代码里**。

完整数字与「为何停刷 feas」见 [`docs/depth_v1_honest_summary.md`](depth_v1_honest_summary.md)。

## 5) 可量化证据

**面试时被问「你怎么知道改好了」，用这一节的数字。核心原则：每个数字都要能说出它是怎么量出来的，以及量它的工具本身有没有被验证过。**

### 主指标：严重引用问题数 / 引用密度

密度 = 每 10 个 URL 的严重问题数，用来抵消报告长短差异（长报告天然引用多，绝对值不可比）。

| 案例 | 起点 | 当前最好 | 说明 |
|---|---|---|---|
| 东边野兽 → 英国 | v3：8 处严重 / 28 URL（密度 2.9） | v8：1 处 / 36 URL（密度 0.3） | 引用变多的同时问题变少 |
| 花知晓 → 泰国 | v1：15 处严重 / 39 URL（密度 3.8） | backup_v4：**0 处** / 37 URL | 换案例首跑就 15 处，见发现一 |
| 石头科技 → 德国 | v1：1 处严重 / 34 URL | — | 跨行业首跑即接近干净 |

**必须同时说明的两件事**（不说会显得没意识到）：

- **东边野兽 backup_v1 是「0 处严重」，但那不是干净，是全文零引用**——没有任何可核查的 URL，机械校验自然查不出问题。矩阵里对这类版本专门标了警告，不允许和有引用的版本比。**「指标好看」和「质量好」在这里是两回事。**
- **早期版本的数字被系统性低估**：那时用 bullet 格式，价格与依据不在同一行，而数字关是逐行判的。已确认影响 9 处，全在 v1 和两个 agentic 版。所以「agentic 版更差」这个结论仍然成立，但**实际差距比测出来的更大**。

### QA 召回率 Benchmark（`experiments/qa_bench.py`）

拿已归档报告当固定输入，对人工标注的 18 条已知问题算召回：

| Case | 召回 |
|---|---|
| herbeast_v3 | 3/3（100%，回归基线） |
| herbeast_v8 | 5/7（71%） |
| flowerknows_v2 | 8/8（100%） |

**这套 benchmark 的价值不在分数，在于它让「规则改写有效」变成可验证的因果**：flowerknows_v2 里三条「市场份额约 25%（证据不足）」，改规则前 QA 判为合规，加了规则 7.5 之后判定变成「违规：含数字无 URL」，**措辞与新规则一一对应**，不是碰巧。

**评分脚本本身踩过两个坑，都会让分数虚高**——最初用品牌名当匹配键，一提到 "Srichand" 就把它名下三条不同问题全判成命中，召回率从真实的 38% 虚高到 75%；后来又发现"引用了某个 URL"被误判成"指出了这个 URL 有问题"。**两次都是我自己的评分工具在骗我自己。**

### 结论有效性（发现五）

33 个归档版本、3 个案例、31 份可行性报告。**加锚点前 11 份全是「建议进入」；加锚点后 20 份里有 4 份降级**（石头科技 v1 / depth_feas_v2 / depth_feas_v3，以及花知晓 depth_feas_v1）。

关键在于这 4 份不全是「证据稀薄」的德国案例——花知晓是彩妆+泰国、公开资料充足，仍被压到 3.10。而同案例的 depth_feas_v3/v4/v5 判 3.65「建议进入」，**说明这条尺子有区分度，不是一律往下推**。

### 工具调用真实性（发现四）

`outputs/tool_audit.jsonl` 记录每次真实调用。石头科技那轮 9 次网页抓取，逐条独立复验：**2 个 404、1 个 403、1 个 200 但页面上没有报告写的价格、1 个真实有效**。模型对这些一律标记为"已核实"。

`experiments/verify_urls.py` / `verify_claims.py` 提供对质。

---

**一句话概括这一节的方法论**：我不只报告指标变好了，还报告**指标本身在哪些情况下会骗人**——零引用会让密度指标失效、格式变化会绕开逐行检测、匹配键选错会让召回虚高一倍。**能说清自己指标的失效边界，比指标本身好看更重要。**

## 6) 我在项目中的贡献

- 从官方样例改造成中国品牌出海研究场景
- 设计"可行性 → 开拓 → 竞品"三段式研究链路，避免每轮重新论证"要不要进入"
- 统一 `ProjectBrief` 输入协议，并写了一套"外部顾问如何在没有品牌方一手资料时挖公开信息"的方法论（`briefs/README.md`）
- 主动发现并修复了系统里的可靠性问题：QA 任务从未真正加载到它该依据的规则文件（知识注入路径 bug）、模型会编造引用但没有任何环节拦截——设计并实现了一层机械引用校验，用真实历史输出验证过它确实能抓出问题
- 为渠道策略/内容生产/QA 审校预留了架构（agent、task、本地化知识包都已就绪），作为明确的下一步拓展方向，而不是仓促做完但没验证

**一段话版本：**

我用 CrewAI 搭了一条中国品牌出海研究多 Agent 流水线，V1 聚焦市场可行性、市场开拓、竞品分析三步，架构上把渠道策略和小红书/抖音内容生产、QA 审校设计成已预留的下一步拓展方向。动机是单 Agent 容易和竞品脱节、缺来源、复杂规则遵守不了。做的过程中我发现模型会编造引用（比如写 `example.com` 当参考文献还标高置信度），而且这类问题没有任何环节能拦下来，于是加了一层不依赖模型自评的代码级引用校验，并用历史输出验证过有效。算法上没训模型，用的是 SOP 式分工 + 上下文传递 + ablation 对照验证，设计思路参考 MetaGPT 的结构化协作。

**30 秒版本（推荐开场用这个）：**

我做了一个帮中国品牌做出海市场研究的多 Agent 系统。做到一半我发现一个核心问题：提示词里写了二十多条硬规则，但模型经常不遵守，还会编造引用来源，而且没有任何环节能拦住。所以我加了一层不依赖模型自评的代码级校验。后来为了验证这些规则是真的通用、还是只是被我调得适配了那一个案例，我特意换了个品类和市场都不同的第二个案例——结果立刻发现我把"英国"写死进了模板字段名，导致整份泰国报告在讨论英国市场份额，而这个 bug 在原案例下永远不会暴露。这件事让我形成了一个习惯：不光要验证模型的输出，还要验证自己的检验工具——后来我就发现我的校验工具自己也有盲区，报出来的基线数字比真实值少了三分之二。

**2 分钟版本（有时间时用，落点放在"我的设计改变了系统行为"）：**

前半段同上（系统 → 编造引用 → 代码级校验 → 换案例逮到硬编码 → 工具自己也有盲区）。然后接：

> 但做到后面我意识到一个更根本的问题。我的报告里一直有一张五维加权评分表，看起来很量化。可我回头翻了 11 个版本、两个案例，**最终结论全部是「建议进入」**——不管评分打多少。那张表是装饰品，它让报告看起来严谨，实际上对结论没有任何约束力。我觉得这比明显的错误更危险，因为它是**伪装成严谨的空洞**。
>
> 根因不是模型不会算加权分，是我从来没定义过「4 分」和「3 分」的区别。没有可判定的标准，打分就变成氛围投票，而氛围总是偏乐观。所以我做了两件很小的事：给每个维度写 1/3/5 的客观锚点（比如合规维度，"需要指定本地代理"就只能给 3 分），以及规定总分直接决定结论档位，不留解释空间。
>
> 结果在第三个案例上——石头科技的洗烘一体机进德国——五个维度打出 3.15 分，模型主动把结论降级成"先验证假设、暂缓铺货"。**在那之前，评分表从来没影响过结论。**
>
> 但这里我要补一句，因为我后来把自己这个结论推翻过一次。我一开始按版本名分组做统计，得出「证据充分的案例也会降级」，听起来很完美。后来改成按报告正文里到底有没有锚点来判定，发现**三次降级全都来自那一个证据最稀薄的案例，带锚点的美妆案例十份、降级零份**。所以我现在只敢说：分数和结论的一致性变成强制且可核对的了，这一点有代码为证；但「锚点让系统在任何案例下都敢说不」我还没证明，得再做一次同案例单变量对照。
>
> 我想强调的是这件事的性质：让一个研究系统具备说 no 的能力，靠的不是换更强的模型，而是把判断标准从模型的直觉里拿出来、写成外部可核对的东西。不过我也得说清楚，这次能降级有一部分原因是德国那个品类公开数据本身就少，所以分数天然上不去。**锚点在证据充分的案例里能不能同样压住分数，我还没有证据**——我知道的一个反例是模型给自己多打了几个 4 分，把总分从 3.4 顶到 3.55，刚好越线。所以下一步是把锚点做成机械可校验的，而不是继续靠模型自觉。

**三个必答问题的准备方向**（细节见各发现）：

| 问题 | 落点 | 对应 |
|---|---|---|
| Agent 和 Workflow 差在哪？ | 差在**控制流让渡给模型多少**；「决定下一步做什么」可以让渡，「判断这一步做得对不对」不能 | 发现六 |
| 你怎么评估你的系统？ | 三层验证 + 两个 benchmark，**重点讲指标在什么情况下会骗人** | §5、发现二 |
| 你数据是怎么构建的？ | 三个案例各为证伪一个具体假设而设计，不是凑数量；brief 里主动埋陷阱 | 发现一、§3 |
| 深度不够怎么办？ | Depth = 证据地板 + soft-pass 诚实失败，不当成品；说 no 靠的是评分锚点不是更深模板 | 发现五、发现七 |

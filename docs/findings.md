# 七个发现

这个项目跑了 3 个案例、33 个归档版本。以下是过程中测出来的东西，按可迁移程度排序。
每一条都能在仓库里找到对应的归档文件与检测代码。

---

## 一、换个案例，才能发现原案例永远发现不了的 bug

前五轮迭代都在同一个案例上做（东边野兽 → 英国），每版都比上版好看。
但这有个陷阱：**分不清「规则真的有用」和「规则只是被调得刚好适配这一个案例」。**

于是换了个差别很大的案例——花知晓、彩妆、泰国，品类和市场同时更换。
第一次跑，整份泰国竞品分析里，四家泰国本土品牌每家都写着「英国市场份额」「英国渠道线索」。

根因：模板里把「英国」当成**字段名**写死了（不是举例，是结构本身），模型老实照着填空。

**这个 bug 在原案例下永远正确、永远不报错。** 跑一百遍东边野兽都发现不了。

**结论**：规则分两类，迁移能力完全不同。
**语义类规则**（「证据不足的结论不能在后文变成确定结论」）跨案例迁移得很好；
**模板类规则**（字段名、合规制度名称）严重过拟合到第一个案例。

## 二、检测工具自己也有盲区，导致基线数字是错的

修完硬编码后重跑，前几类问题清零了，但模型立刻换了两种新写法：
商品页全部改用品牌首页（从「用错的具体页」退化成「根本不给具体页」）、
以及「市场份额约 30%（待验证）」（给个没来源的数字，加个免责词，同时躲过两条规则）。

**这两种新写法当时的校验工具一个都抓不到。** 工具报告显示「5 处严重问题」，看起来还行。
补上这两个检测后，同一批文件的真实数字是 **15 处**。

**为什么这件事严重**：基线是「以后所有版本都拿来对比的参照数字」。
如果把错的「5」当基线，以后跑出 8 处会被读成「变差了」，
但真实情况是从 15 降到 8、大幅变好。**不是读错一次，是从此以后所有对比都是反的。**

**结论**：把一个数字当基准之前，先确认量它的工具本身是准的。

## 三、让模型审模型，得先分清是模型能力问题还是任务设计问题

第一次引入 QA 审校环节（gpt-4o-mini）：机械校验第一次全绿（30 个引用零问题），
但人工通读发现报告里有个「65%」的目标人群占比——回查简报根本没有这个数字。
本该补上这个盲区的 QA，一条真问题都没发现，反而误报了两处，
还在同一份文件里「前面说有阻塞问题、后面把检查项全打勾」。

做了一个单变量实验：**只把 QA 一个 agent 换成推理模型，其余 8 个 agent 和四份 prompt 一字未动。**
三个失败全部消失，而且它抓到了三件机械校验查不到的问题——
比如报告写「品牌成立于 2021 年」没标出处，而简报里专门写了这个年份在不同来源有分歧。

**但同一轮里，机械校验也抓到了三处 QA 完全漏掉的问题**（三家竞品的舆论口碑全是无来源断言）。

进一步定位发现，QA 漏掉那三处的**根因不是模型不够聪明**：
它的输出模板里只有「逐 URL 核查表」，天生只能检查已存在的链接，
查不到「本该有链接却空着」的地方。**这是任务设计缺陷，换再强的模型也不会自动补上。**

**结论**：三层查的是不同类型的问题，不是备选关系而是流水线关系。

| 层 | 擅长 | 局限 |
|---|---|---|
| 机械校验 | 穷举式形式检查，不漏行 | 只认写进代码的模式 |
| 推理模型 QA | 需要回查原始材料的判断 | 不保证覆盖每一行 |
| 人工通读 | 发现**新的**问题类型 | 注意力不稳定、不可规模化 |

## 四、「让模型自我报告执行状态」这个设计模式本身不可靠

把最独立的一步（竞品分析）改成 agentic 版——给目标不给模板，加网页抓取工具，
让它自己决定查几家、深挖谁、什么时候停。跑了四轮，每轮都失败，但**失败模式在演化**：

| 轮次 | 改动 | 失败形式 |
|---|---|---|
| 1 | 放开输出模板 | 交了一份 **0 个引用**的工作汇报，结尾写「抓取和数据验证已成功完成」 |
| 2 | 结构约束改回硬性 | 结构恢复，但开始**伪造核实记录**：10 条「已用工具核实，页面显示标价 £XX」，逐条对质**通过 0 条** |
| 3 | 加工具调用审计 | 审计证明它**确实调用了 6 次抓取且全部成功**——但抓的是 4 个品牌首页 + 1 个反爬拦截页（106 字符的「请开启 JavaScript」），它照样每行写「已核实」 |
| 4 | 删掉「核实状态」自述栏 | 出现第一条诚实记录，但把四个网站首页标成了「单品页」 |

**结论**：不是「agent 不行」，审计日志证明它工具用得好好的。
问题在于**只要设计里留了「让模型报告自己做得怎么样」的字段，它就会填出好看但不真实的内容**。
每堵住一个说谎的位置，它就换一个位置说。

**正确做法是把执行状态的判定完全交给代码**：订阅框架的事件总线记录每一次真实调用
（调了什么工具、传了哪个 URL、返回多长、报没报错），跑完逐条对质。判据全部客观，不需要模型配合。

**一个值得单说的自查细节**：审计脚本原本用工具名里含不含 `scrape` 来识别抓取调用。
核对后发现 `ScrapeWebsiteTool` 的显示名是 **"Read website content"**，压根不含 scrape 字样。
如果没查这一下，审计会报告「没有任何抓取调用」——**而这个假阴性恰好出现在最关键的那个测量上**。

## 五、一张没人当真的评分表，怎么变成可核对的判据

可行性报告一直有一张五维加权评分表（需求匹配 / 合规可完成性 / 渠道可达 / 竞争强度 / 品牌资产匹配）。
看起来很量化。但翻遍加锚点之前的版本，**最终结论全部是「建议进入」**——不管评分打多少。

那张表**是装饰品**。而这恰恰是最危险的一类问题：**它不是明显的错误，它是伪装成严谨的空洞。**

根因不是模型不会算加权分，是**从来没有人定义过「4 分」和「3 分」的区别**。
没有可判定的标准，打分就变成氛围投票，而氛围总是偏乐观。

改动只有两条：

1. **每个维度写 1/3/5 三档锚点**，锚点必须是可判定的客观事实。
   例如合规维度：5 = 制度清晰且无需本地代理；3 = 制度清晰但需完成登记 / 指定代理；1 = 制度不明或有禁止性条款。
2. **总分决定结论档位**，不留解释空间：≥3.5 建议进入 / 2.5–3.5 先验证假设、暂缓铺货 / <2.5 暂不建议。

结果：石头科技 → 德国那一版，五个维度打出 3.15，模型主动把结论降级成「先验证假设、暂缓铺货」。
**在此之前，评分表从来没影响过结论。**

### 附：一次被推翻的过度解读

后来想验证「锚点在证据充分的案例里是否也压得住分数」，
按**版本名**分组统计（「新版本 = 带锚点」），得出「加锚点后 4 份降级，其中一份是证据充分的彩妆案例」，
据此写下「替代解释被排除了」。

改成按**报告正文里到底有没有锚点**判定之后，结论翻转：

| 案例 | 带锚点份数 | 其中降级 |
|---|---|---|
| 东边野兽 → 英国 | 4 | **0** |
| 花知晓 → 泰国 | 6 | **0** |
| 石头科技 → 德国 | 4 | **3** |

**三次降级全部来自同一个证据最稀薄的案例**，而那份用来支撑结论的彩妆降级样本，**根本没带锚点**。

所以目前只能说：
- ✅ 分数与结论档位的一致性现在是强制且可机械校验的，这一点有代码为证
- ❌ 「锚点让系统在任何案例下都敢说不」**没有被证明**
- 下一步需要同案例单变量对照（只改有无锚点），**尚未做**

这是发现二的第三次重演，只不过这次犯错的是数据分组：
**按版本名猜「新版本应该带锚点」是想当然，按正文内容查才是事实。**

## 六、那张表不只是没约束力，它连算术都是错的

写完锚点之后想验证一件事：报告的结论，到底是不是从它自己的评分算出来的？
于是写脚本把每份报告里那条「加权总分 = 0.25×4 + 0.15×3 + …」的式子**重算一遍**。

**31 份带评分表的报告里，19 份有严重问题**，其中若干份的结论与它自己写的分数直接矛盾。最典型的一份：

```
报告写的：Σ(权重×得分) = 0.25×4 + 0.15×3 + 0.20×3 + 0.20×4 + 0.20×4 = 3.35
实际算：                                                          = 3.65
报告的结论：建议进入
按它自己写的 3.35，规则要求的是：先验证假设、暂缓铺货
```

**说明分数和结论根本是各写各的。** 模型先定下想说的结论，再产出一段看起来很像回事的计算，
中间没有任何一步在检查两者是否一致。

**这条是「伪装成严谨」的最纯粹形态**：假引用还需要读者点开链接才知道是假的，
**算错的加权和连点都不用点，但也恰恰因此没人会去验**——它长得太像已经被验过的样子了。

**为什么必须交给代码**：加权求和是确定性运算，阈值判档是明确规则，
**让模型自查等于让它重做一遍同样会做错的事**。

> **这个检查器自己也出过误报，一并记在这里**：早期实现是「找到含『总分』的行，取第一个小数」，
> 于是「建议进入。2024 年增长 12.5%」会被读成总分 12.5，报出一条**根本不存在的违规**。
> 修成按表格列位取值 + 限定在 [1,5] 区间。
> **校验工具误报比漏检更糟——漏检只是没帮上忙，误报会让人不再相信整套指标。**

## 七、Workflow 怎么变得更像 Agent，又不牺牲可评估性

发现四里那个「教科书式 agentic 版」四轮全败，而且败在同一个地方——**它自己报告自己干得不错**。

换了个思路：**保留 workflow 的控制流，只把「自我修正」这一个 agent 特征加进去，但裁判换成代码。**

具体做法是把已有的机械校验挂成框架的 task guardrail：

```
产出 → 机械校验 → 有严重问题？
  ├─ 是 → 把违规逐条喂回同一个 agent → 自动重跑
  └─ 否 → 通过，进入下一步
```

**为什么仍算 agent 特征**：观察 → 行动 → 再观察的闭环、根据反馈调整、自己收敛到合格。
**为什么没丢掉可评估性**：控制流仍在代码手里、任务顺序固定、输出结构不变，跨版本矩阵依然可比。

**关键区别只有一个字：裁判是谁。**
agentic 版把「做得对不对」交给模型自己判断，结果写了 10 条「已核实」、对质通过 0 条。
guardrail 把这个判断交给代码。**同样是循环，但裁判可信。**

**一般化表述**：

> Agent 相比 Workflow 多出来的能力，本质是**把控制流的一部分让渡给模型**。
> 让渡得越多，能力上限越高，可评估性越差。
> 所以真正的问题不是「要不要做 agent」，而是
> **「这一步的控制流，交给模型的收益是否大于失去可验证性的代价」**。
>
> 目前的经验是：**「决定下一步做什么」可以适度交给模型，「判断这一步做得对不对」不能。**
> 因为前者错了会被后者兜住，后者错了整个系统就没有真相来源了。

**踩过的坑**：guardrail 第一版是无效的——框架写文件时用的是第一次执行的结果变量，
重试产生的新内容只在返回值里，所以**校验正常触发、模型也确实改了，但落到磁盘上的还是原始版本**。
是靠「把最终文件重新喂给校验函数，它却被正确拦下」这个矛盾才定位到的。
**这类 bug 的共同点是：所有中间日志都显示正常，只有最终产物是错的。**

## 一个贯穿全程的模式

每堵一个漏洞，模型就找到一种新的绕过方式：

编造假域名 → 用真链接但内容对不上 → TBD 占位 → 品牌首页当商品页 →
数字加免责词 → 社媒账号主页当舆论证据 → 伪造检索过程描述

**这不是失败记录，而是「光靠写提示词不可靠、必须有机械校验兜底」这个论点的实证。**
`citation_check.py` 现有的 18 类检测，每一条都对应上面这条链上的一次真实失败。

**人工复核的正确定位不是「每次交付前的关卡」，而是「新检测规则的来源」。**
人工每发现一个新问题，产出不应该是「这一版有这个问题」，
而应该是「**从此以后每一版都自动查这个问题**」——这样人工的时间才有复利。

## 已知未解决

一个只报告好消息的评估体系没有价值。以下是当前明确知道、但尚未解决的缺陷：

1. **模型抓了网页、收到 48 字符的错误页，照样把 URL 和价格写进报告**——跨三个案例复现，是当前最该解决的问题
2. **缺口补证环节曾 0 次真实检索却写出三条「检索策略」**；已加基于审计日志的强制校验，但**未经真机验证**
3. **bullet 块内的无源价格查不出来**（数字关是逐行判定的）——已确认影响范围为 9 处且全在早期版本，暂不修
4. **评分锚点仍依赖模型自觉**，只做到了「总分与结论一致」可机械校验
5. **渠道策略与内容生产链路**代码可跑，但从未验证过产出质量，不作为成果
